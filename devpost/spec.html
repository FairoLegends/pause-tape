PAUSE TAPE
TECHNICAL SPEC

The blueprint for how Pause Tape is built: one static web page (HTML + CSS + JS, no framework), tapes stored in the browser's localStorage, a .ics file made in the browser, VHS effects as a CSS layer driven by one --vhs number, hosted free on GitHub Pages.

How This Works: Unity → Web

Unity: Scene + Hierarchy
HTML

index.html holds all 7 screens as nested elements. Switching screens = SetActive.

Unity: Materials / UI look
CSS

Colors, the two fonts, the CRT frame, and the VHS layer.

Unity: MonoBehaviour scripts
JS

Clicks (onClick), timers (Update), saving, building the calendar file.

Unity: PlayerPrefs + JsonUtility
localStorage

The tape list saved as JSON text in this browser. No server, no accounts.

Why this shape: GitHub Pages only serves files, and everything Pause Tape needs can happen inside the browser. The files you write are exactly the files that go online.

The Core Journey Through the System

Nothing is saved between pressing ▶ and pressing "I'm back on it". That's why closing the app mid-timer records nothing, and a locked tape played early goes back to locked, with no extra code.

The .ics File

BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Pause Tape//EN
BEGIN:VEVENT
UID:t_1727650000000@pause-tape
DTSTAMP:20260930T070211Z
DTSTART;VALUE=DATE:20270110
DTEND;VALUE=DATE:20270111
SUMMARY:▶ NO SIGNAL — tape ready
DESCRIPTION:First step: …
BEGIN:VALARM
ACTION:DISPLAY
TRIGGER;RELATED=START:PT8H
END:VALARM
END:VEVENT
END:VCALENDAR

All-day: VALUE=DATE, ending the next day.

First step in the reminder: the DESCRIPTION, so you know what to do before opening the app.

08:00 WIB alarm: PT8H = 8 hours after the day starts in the device's own time zone. On your devices, that's 08:00 WIB.

To test in the build: Outlook on your laptop for the demo (check the event and alarm appear), and your Android phone (Google Calendar often ignores imported alarms). Problems go into the README's Known limitations.

Decisions, Simplifications, Risks

YOURSLearner decisions
  • Learn basic web code, only what Pause Tape uses, explained through Unity/C#.
  • Static site on GitHub Pages so judges can open a link; build and record locally; deploy in 6-ship.
  • Everything in the browser: localStorage (like PlayerPrefs), .ics made in the browser, VCR font stored in the project.
  • HTML/CSS/JS, no framework.
  • VHS as a CSS layer driven by --vhs, like VHSDriver. No curved distortion needed: nostalgic, not scary.
  • Flicker slow and soft; with "reduce motion", flicker and glitch off, scanlines stay.
  • Demo: .ics opened in Outlook on the laptop, all in one recording. Test Android too, and note any problem in the README.
  • VCR font: VT323 (SIL Open Font License, safe for a public repo).
  • Local server: python -m http.server 8000.
AI DEFAULTImplementation details (accepted)
  • JS modules, which is why a local server is needed.
  • System monospace for answers.
  • Minutes rounded to the nearest minute, minimum 1.
  • Pacing: blue screen ~1.2 s, ~2.5 s between answers, NO SIGNAL ~1.2 s.
  • --vhs: 0.3 record, 0.5 shelf/results, 1.0 playback.
  • App files at the repo root.
YOUR UNKNOWN"Is the web VHS effect like a Unity shader?"

A web shader (WebGL) exists, but it only processes what it draws itself, not HTML text and buttons, unlike a URP fullscreen pass over the whole camera image. So the effect is a click-through CSS overlay plus a per-answer glitch, with one intensity variable set from JS: the same control pattern as VHSDriver.

Checked in the build: compare the Record Screen (0.3) and Playback (1.0) side by side; the difference must be visible (prd.md > Playback).

SIMPLIFIEDWhat was kept small, and why
  • CSS effects instead of WebGL: WebGL can't post-process HTML; the full version means redrawing the whole UI in a canvas.
  • localStorage in one browser instead of accounts and a database (accounts and sync are deferred).
  • A downloaded .ics instead of push notifications, which would need a server and permissions.
  • No in-app delete/reset: rehearse by clearing localStorage in DevTools (delete is deferred in the PRD).
  • Hand-written screen switching instead of a framework: enough for 7 screens.
FAILURE MODESWhere it could break
  • Saved data missing or broken → empty shelf with "Record your first tape"; never a crash.
  • Calendar ignores the alarm or can't open the file → the tape is still saved; the limitation goes in the README.
  • Wrong "today" near midnight → local date strings only, never UTC.
  • Font fails to load → falls back to system monospace.
